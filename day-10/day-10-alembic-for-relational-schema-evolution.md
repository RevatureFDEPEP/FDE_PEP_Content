# Alembic for Relational Schema Evolution

> *Day 10: Integrate the Slice + Scaffold Reporting Service + Week 2 Review — PEP 4-Week Curriculum*
> *Week 2: Operationalize + First Vertical Slice (Question Authoring)*

## Overview
The reporting service uses Postgres — and unlike Mongo (where Day 8's `question-management-service` evolved schema via per-document `schema_version`), Postgres needs **migrations**: explicit, ordered, reversible changes to tables and indexes. Alembic is the SQLAlchemy-native migration tool. Today we initialize Alembic in the scaffolded service, create the first migration from an empty model set (the placeholder), and practice the upgrade/downgrade workflow. The skill that matters more than the commands is the *discipline* — always review autogenerated migrations, never edit applied ones, and treat the migration history as code under review.

## Why Migrations (vs Mongo's `schema_version`)

Postgres is strict: a column either exists or it doesn't, and existing rows must satisfy any new NOT NULL constraint. You can't add `quiz_attempt.score INT NOT NULL` to a table with a million rows without saying what existing rows should hold. Alembic gives you a versioned chain of SQL operations to evolve the schema safely:

```
revision a1b2: initial schema (no tables)
revision c3d4: create quiz_attempts table
revision e5f6: add score column with server_default=0
revision g7h8: drop server_default, make score NOT NULL
```

Each migration knows how to go up (`upgrade()`) and how to come back down (`downgrade()`).

## Initial Setup in the Scaffold

From inside `services/reporting-and-analytics-service/`:

```bash
# 1. Initialize an async-flavored alembic project
alembic init -t async alembic

# This creates:
# alembic/
#   env.py
#   script.py.mako
#   versions/
# alembic.ini
```

The `-t async` template configures `env.py` for SQLAlchemy's async engine, which matches our `app/db.py`.

### Configure `alembic.ini`

Don't put the database URL here — read it from settings instead. Leave `sqlalchemy.url` empty in `alembic.ini`:

```ini
# alembic.ini (excerpt)
[alembic]
script_location = alembic
sqlalchemy.url =
```

### Wire `env.py` to App Settings and Metadata

```python
# alembic/env.py (relevant edits)
import asyncio
from logging.config import fileConfig
from alembic import context
from sqlalchemy.ext.asyncio import async_engine_from_config
from sqlalchemy import pool

# Make app importable
import sys, pathlib
sys.path.insert(0, str(pathlib.Path(__file__).resolve().parents[1]))

from app.settings import settings
from app.db import Base          # SQLAlchemy DeclarativeBase
import app.models                # noqa: F401 — registers models with Base.metadata

config = context.config
if config.config_file_name is not None:
    fileConfig(config.config_file_name)

# Inject the URL from app settings
config.set_main_option("sqlalchemy.url", settings.database_url)

target_metadata = Base.metadata

def run_migrations_offline() -> None:
    context.configure(
        url=settings.database_url,
        target_metadata=target_metadata,
        literal_binds=True,
        dialect_opts={"paramstyle": "named"},
    )
    with context.begin_transaction():
        context.run_migrations()

def do_run_migrations(connection):
    context.configure(connection=connection, target_metadata=target_metadata)
    with context.begin_transaction():
        context.run_migrations()

async def run_migrations_online() -> None:
    connectable = async_engine_from_config(
        config.get_section(config.config_ini_section, {}),
        prefix="sqlalchemy.",
        poolclass=pool.NullPool,
    )
    async with connectable.connect() as connection:
        await connection.run_sync(do_run_migrations)
    await connectable.dispose()

if context.is_offline_mode():
    run_migrations_offline()
else:
    asyncio.run(run_migrations_online())
```

**Critical gotcha:** the `import app.models` line. Autogenerate compares `Base.metadata` against the database. If your model modules aren't imported before `target_metadata = Base.metadata` is read, *autogenerate sees no tables* and silently produces an empty migration. Always import the models module(s).

## The Day-to-Day Commands

```bash
# Generate a new migration by diffing models vs database
alembic revision --autogenerate -m "init"

# Apply all pending migrations
alembic upgrade head

# Roll back one revision
alembic downgrade -1

# Show current head
alembic current

# Show history
alembic history --verbose

# Generate SQL for a migration without applying it (useful for review)
alembic upgrade head --sql
```

### Worked Sequence for Today

```bash
# Bring up the database (added to Compose in Topic 6)
docker compose up -d reporting-postgres

# Generate the first migration
alembic revision --autogenerate -m "init schema ping table"
# → alembic/versions/a1b2c3d4_init_schema_ping_table.py

# REVIEW the generated file (do not skip this)
$EDITOR alembic/versions/a1b2c3d4_init_schema_ping_table.py

# Apply
alembic upgrade head

# Verify
docker compose exec reporting-postgres psql -U reporting -d reporting \
  -c '\dt'   # should show _schema_ping and alembic_version

# Roll back to prove downgrade works
alembic downgrade -1

# Re-apply
alembic upgrade head
```

## What Autogenerate Catches — and What It Misses

Autogenerate runs a metadata diff. It **catches**:

- Added/dropped tables.
- Added/dropped columns.
- Most column type changes (with `compare_type=True` in `env.py`).
- Indexes and unique constraints (with `compare_server_default=True`).

It **misses**:

- Column renames (it sees `drop old + add new` — data loss if applied blindly). You must hand-edit to `op.alter_column(..., new_column_name=...)`.
- Check constraint changes (often).
- Permissions, grants, triggers, functions — anything not modeled by SQLAlchemy.
- Server-side defaults if you haven't set `compare_server_default=True`.
- Data migrations (moving values between columns). Always hand-write these.

**The rule:** every autogenerated migration is a draft. Read it before applying.

## Server Defaults Are a Trap

Adding a NOT NULL column to a populated table:

```python
# ❌ Wrong — fails on existing rows
op.add_column('quiz_attempts', sa.Column('score', sa.Integer(), nullable=False))

# ✅ Right — two-step
op.add_column('quiz_attempts',
    sa.Column('score', sa.Integer(), nullable=False, server_default='0'))
# Optionally, in a follow-up migration, drop the default:
op.alter_column('quiz_attempts', 'score', server_default=None)
```

`server_default` is database-side (Postgres fills existing rows during the migration). Pydantic/SQLAlchemy `default=` is Python-side and only fires for new inserts — it does *not* fix existing rows.

## Migrations in CI and on Deploy

Today's local cycle is `alembic upgrade head` by hand. The deployment pipeline pattern (set up in Week 4 for reporting):

1. CI builds the image with `alembic/` baked in.
2. The ECS task definition (or a one-shot ECS task) runs `alembic upgrade head` *before* the new app version starts serving.
3. New app version starts only after migrations succeed.
4. If migrations fail, no new code is exposed; roll forward by fixing the migration, not by manual DB tinkering.

This is why migrations must be reversible and fast — they're in the critical path of every deploy.

## Anti-Patterns

- **Editing an applied migration.** The hash is the identity; editing breaks every other environment. Add a new migration instead.
- **Skipping the diff review.** Autogenerate is a starting point. Renames, data migrations, and drops need human eyes.
- **Squashing migrations to "clean up history."** Looks tidy, breaks staging. Append, don't rewrite.
- **Letting the DB and migration head drift in dev.** Always `alembic upgrade head` after pulling main.
- **Forgetting to import models in `env.py`.** Silent empty migrations. Always `import app.models` (or whichever module declares classes).
- **Writing data migrations with the ORM.** Use raw SQL via `op.execute(...)` — ORM model classes drift over time and a migration written against today's ORM may fail next year.

## Key Takeaways
- Postgres is strict; Alembic gives you ordered, reversible schema changes.
- Initialize once with `alembic init -t async`; wire `env.py` to `app/settings` and `Base.metadata`.
- `alembic revision --autogenerate -m "..."` drafts a migration; **always review** before `upgrade head`.
- `alembic downgrade -1` rolls back; both directions must work or you have an outage on rollback.
- Use `server_default` to backfill existing rows for new NOT NULL columns; use raw SQL for data migrations.
